# KIVO 2.0 — 第一阶段代码审查

审查日期：2026-11-27
审查范围：GitHub main 分支可读取文件、README、Config.ini、依赖、构建/测试工作流、SPST.iss、tests/test_source_safety.py，以及 main.py 的已读取部分和已有测试所覆盖函数。
审查限制：main.py 约 596 KB；当前审查不能等同于逐行、运行时/Windows 真机审查。后续继续按功能分段检查并运行测试。

## 摘要
- 应用已具备较丰富的功能，版本标识为 1.4.30，构建工作流发布单文件 EXE 和安装程序。
- 主要工程风险是单文件主程序过大、测试偏向源码静态断言、依赖与构建环境复现性、发布/更新/授权尚未形成产品闭环。
- 本次不修改 main.py 或既有发布文件；仅新增审查记录与后续路线图，所有工作在独立分支上。

## 已确认的优点
1. 有源码安全回归测试及 CI workflow。
2. 测试覆盖粘贴队列成功条件、SendInput 部分失败、剪贴板内存释放、原子写、INI 注入清理、下载链接清洗、OCR 框合并、HTTP URL 校验等风险点。
3. 通过 ConfigParser interpolation=None 避免百分号插值问题。
4. EXE 构建与 Inno Setup 安装程序工作流已经存在。
5. 更新程序描述包含 SHA256 与 RSA 签名验证设计，需在后续审查验证实现与信任根。
6. 安装器设计明确保留 AppId 和用户数据目录，便于原地升级。

## 优先问题与建议

### P0 — 发布安全与用户信任
- 更新机制：下一阶段审查签名验证代码、签名公钥嵌入方式、版本/降级策略、下载校验与异常路径。不可仅凭README/版本注释确认安全。
- AI API 配置：目前 README 指出 API Key 保存本地 Config.ini。建议提供敏感设置的显式说明、备份/日志脱敏、Key清除机制；不能把密钥提交仓库。
- 媒体下载：检查 URL 验证、重定向、文件名处理、文件大小/超时限制及外部命令执行边界。
- 发布流程：考虑固定依赖版本、校验第三方 Actions、发布资产与源码版本一致、避免误发布。

### P1 — 可维护性
- main.py 体积约 596 KB，UI、系统接口、网络/API、AI、OCR、下载、配置及功能模块耦合风险较高。建议逐步拆分模块，迁移过程中保持功能行为与热键兼容。
- 采用模块边界：app/bootstrap、config、storage、clipboard、hotkeys、capture/annotation、ocr、translation、ai/providers、download、update、ui panels。
- 建立可注入依赖与接口；核心逻辑避免直接依赖 Tk/Windows API，便于跨平台CI测试。
- 加入类型标注、结构化日志、统一错误类型、模块级文档。

### P1 — 测试与稳定性
- 当前测试文件 14 项左右且以源码文本断言/AST加载函数为主；此类测试可防止部分回归，但不能充分证明真实运行行为。
- 新增独立纯逻辑测试、配置往返/备份恢复、下载输入验证、更新签名校验、网络超时/重试、AI provider 请求构造与异常、存储故障测试。
- Windows 真机测试矩阵：Windows 10/11、普通权限、双显示器/缩放、输入法、剪贴板竞争、休眠恢复、热键冲突、安装/升级/卸载。
- 检查线程安全：Tk UI 更新必须通过安全调度；后台任务有取消、超时和关闭清理机制。

### P1 — 构建与依赖
- requirements.txt 包含部分最低版本约束而非完整锁定。建议建立用于构建的锁文件/哈希校验，分离运行、开发、打包依赖。
- GitHub Actions 的依赖瘦身步骤会直接删掉安装目录部分内容。建议明确最小依赖清单、在瘦身后运行导入/OCR smoke tests，减少依赖内部结构变化造成构建失效。
- 检查 Actions 的权限最小化、版本固定、Release 权限及工作流触发范围。

### P2 — 产品与商业化
- 先聚焦“剪贴板 + 截图/OCR + 标注”核心工作流，AI作为可选能力。
- 设计免费/付费功能边界与授权机制之前，先验证用户需求，避免过早引入复杂服务端。
- 优先做官网/产品介绍、隐私说明、变更日志、使用教程、自动更新与反馈入口。
- AI API 用量预算、用户自行提供 Key 的模式、可选服务端模式及数据发送前告知。

## 分阶段路线图
1. 审查基线：逐段审查关键模块、现有测试与工作流；整理风险清单。
2. 测试基建：新增纯逻辑测试、CI lint/测试与构建 smoke tests。
3. 模块化：从低风险纯逻辑模块迁出，不重写主 UI；逐步拆分配置/存储、URL验证、AI providers。
4. UX与产品化：核心工作流、隐私设置、错误提示、帮助与 onboarding。
5. AI功能治理：Provider适配、超时/重试/成本限制、脱敏与用户确认。
6. 发布体系：版本号统一、签名与更新验证、发布资产校验、升级/回滚测试。
7. 商业验证：定价测试、用户反馈、渠道与转化验证；确认需求后再建设授权/付款。
